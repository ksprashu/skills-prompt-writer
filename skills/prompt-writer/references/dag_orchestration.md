# 🕸️ DAG Task Graph & Pure Orchestrator Reference Specification

This document defines the schema, operational state machine, and pure orchestrator protocol for **Modular Orchestration Decks** generated by the `prompt-writer` skill in Heavyweight Mode.

---

## 1. Directory Structure of a Modular Orchestration Deck

When operating in Heavyweight Mode, `prompt-writer` compiles user requirements into a namespaced DAG directory under `.gemini/prompts/<SHORT_ID>/`:

```
.gemini/prompts/<SHORT_ID>/
├── task_graph.json                     # Machine-readable DAG of atomic task nodes
├── orchestrator.md                     # Directives for the Pure Manager thread
├── metadata.json                       # Short ID, status, tags, and execution history
├── prompt.md                           # Compiled entrypoint / overview
└── tasks/                              # Atomic worker prompts (1 per node)
    ├── task_01_<name>.md
    ├── task_02_<name>.md
    └── task_03_<name>.md
```

The `task_graph.json` file dictates task execution order, workspace isolation, model tiering, and blocking verification criteria.

## 3. Pure Orchestrator (Manager) Protocol

The executing main thread operates under strict **Pure Orchestrator Protocol**:

1. **Zero Direct Implementation**: The Manager thread NEVER calls code-editing or file-writing tools directly on target source files.
2. **DAG Evaluation**: The Manager reads `task_graph.json`. It identifies all nodes whose `dependencies` are completely `VERIFIED`.
3. **Subagent Execution (`invoke_subagent`)**:
   - For each ready node, the Manager launches a specialized worker subagent using `invoke_subagent`.
   - Pass the contents of `tasks/<task_file>.md` as the subagent's prompt.
   - Set `Role`, `Model`, and `Workspace` according to the node specification in `task_graph.json`.
4. **Sentry Gatekeeping**:
   - When a worker subagent signals completion, the Manager DOES NOT immediately mark the task as complete.
   - The Manager spawns a **Sentry / Verifier Subagent** using `verification_gate.verifier_prompt`.
   - The Sentry executes tests, builds, or security scans to verify `blocking_criteria`.
5. **State Journal & Sign-off**:
   - If the Sentry confirms all `blocking_criteria` pass, the Manager updates node status to `VERIFIED` in `task_graph.json` and `.gemini/tasks/<SHORT_ID>/state_journal.json`.
   - If the Sentry reports failures, the Manager re-dispatches the worker subagent with failure feedback (capped at `MAX_ITERATIONS=3`).
6. **Reactive Wakeup**:
   - After launching subagents, the Manager stops calling tools. The Antigravity system automatically wakes the Manager up when a subagent sends a message or completes.

## 4. Dynamic Domain Pipeline Templates

### A. 💻 Coding & Engineering (`domain: "coding"`)
- `Node 1: Spec & Data Contracts` (Architect)
- `Node 2..N: Module Builders` (Parallel Builders in `branch` workspaces)
- `Node N+1: Integration & TDD Suite` (pytest / Jest)
- `Node N+2: Code Review & Sentry Audit` (Sentry)

### B. 🎨 UI & Design (`domain: "ui_design"`)
- `Node 1: UX/UI Design System Spec` (Architect)
- `Node 2: Component Layout & CSS Rules` (Builder)
- `Node 3: DevTools Visual Inspection` (Chrome DevTools Subagent)
- `Node 4: Accessibility & Contrast Audit` (A11y Subagent)

### C. 🔒 Security & Hardening (`domain: "security"`)
- `Node 1: Vulnerability Scan` (`run_security_scanner`)
- `Node 2: Mitigation Plan & Patch Drafting` (`create-security-implementation-plan`)
- `Node 3: Proof-of-Concept Verification` (`run_poc`)
- `Node 4: Audit Report Assembly` (`generate-security-audit-report`)

### D. 🔬 Research & Analysis (`domain: "research"`)
- `Node 1: Multi-Source Crawl` (Parallel Codebase Scout + Web Intel + Docs Crawler)
- `Node 2: Synthesis & Fact Extraction` (Analyst)
- `Node 3: OKF Knowledge Bundle Compilation` (Mentor)

### E. 🧪 Verification & Audit (`domain: "verification"`)
- `Node 1: Spec Contract Matcher`
- `Node 2: Dual Test Runner` (pytest + behave)
- `Node 3: Evidence Ledger Audit` (`validate_evidence.py`)
